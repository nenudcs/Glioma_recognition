# 流式加载数据代码修改方案

## 1. 文档目的

本文给出 `Glioma_recognition` 推理服务从“全量加载整个测试集”改为“按病例流式加载”的代码修改方案。官方已确认输入仅包含 NIfTI，本方案及实现不再兼顾 DICOM。

核心目标是将推理阶段的影像内存复杂度从：

```text
O（全部病例影像 + 全部病例结果）
```

降低为：

```text
O（单个病例影像 + 单个病例结果 + 全局轻量特征）
```

同时保持以下外部协议不变：

- `POST /call` 的请求和即时响应不变；
- `request_id`、`evaluation_id` 和 `dataset_path` 的校验规则不变；
- Goal1～Goal5 的结果数据结构不变；
- 最终输出目录结构和文件格式不变；
- 输出全部通过校验后才发布；
- 成功发布后才发送 callback；
- 失败时不发送成功 callback。

## 2. 当前问题

当前推理链路为：

```text
POST /call
→ EvaluationRunner.run()
→ DatasetLoader.load()
→ 一次性构造 CompetitionDataset
→ InferencePipeline.run()
→ 一次性构造所有 PipelineContext
→ OutputWriter.write_staging()
→ OutputValidator.validate()
→ publish
→ callback
```

主要内存问题有三处。

### 2.1 DatasetLoader 保存全部三维影像

`DatasetLoader.load()` 会遍历 `dataset_path`，将全部 NIfTI 序列加载为 NumPy 数组，并保存在：

```text
CompetitionDataset
└─ studies
   └─ series
      └─ image: np.ndarray
```

只要 `CompetitionDataset` 仍被 `EvaluationRunner` 引用，全部影像数组就不会被释放。

### 2.2 Pipeline 保存全部病例结果

`InferencePipeline.run()` 会为每个病例创建一个 `PipelineContext`，并将所有 context 保存在字典中。Goal5 的两个完整三维掩膜也会随 context 一直保留到所有病例推理完成。

### 2.3 Writer 和 Validator 必须等待全量推理结束

当前 Writer 接收完整 `contexts` 字典，统一写出所有病例；Validator 又依赖完整 `CompetitionDataset` 校验掩膜的 shape 和 affine。因此，单个病例推理完成后无法立即写出、校验和释放。

## 3. 设计原则

### 3.1 以 Study 为最小流式单元

一个模型通常需要同一病例的多个序列，因此不建议默认按切片或单序列流式处理。新的默认生命周期应为：

```text
加载一个 Study 的全部 Series
→ 执行该 Study 的 Goal1～Goal5
→ 写出该 Study
→ 立即校验该 Study
→ 提取 Goal2 重复检测所需的轻量信息
→ 释放 Study 和 PipelineContext
```

如果单个 Study 本身仍然超过内存预算，再单独增加 patch、切片或序列级推理；这不属于第一阶段改造范围。

### 3.2 保留现有 StudyTask 和 Result 契约

Goal1、Goal2 拼接检测、Goal3、Goal4、Goal5 仍通过现有 `StudyTask.predict(context)` 接口开发。

各目标模型不负责：

- 遍历整个数据集；
- 创建比赛输出目录；
- 写 `prediction.json`；
- 保存 callback 状态；
- 直接发送 callback。

这样，流式加载改造不会破坏 Goal1～Goal5 的并行开发边界。

### 3.3 保留临时目录和原子发布

每个病例虽然会被立即写出，但仍全部写入：

```text
answer/.{evaluation_id}.tmp-{uuid}/
```

只有所有病例、重复影像文件和最终目录结构都校验通过后，才将临时目录重命名为最终目录。

因此，流式写出不等于提前发布部分结果。

### 3.4 第一阶段不增加并行预取

首版流式实现保持：

- 单个 evaluation 后台线程；
- 单个 Study 顺序处理；
- 不在内存中预取下一个 Study；
- 不增加新的第三方依赖。

先解决 OOM，再根据实际性能数据决定是否增加一个有界预取队列。

## 4. 目标调用链

改造后的目标链路为：

```text
POST /call
→ JobManager 提交后台任务
→ EvaluationRunner 创建 staging 目录
→ DatasetLoader.iter_studies(dataset_path)
   → 加载 Study A
   → Pipeline.run_study(Study A)
   → DuplicateTask.update(Study A / Context A)
   → Writer.write_study(Context A)
   → Validator.validate_study(Study A)
   → 释放 Study A 和 Context A
   → 加载 Study B
   → ……
→ DuplicateTask.finalize()
→ Writer.write_duplicates()
→ Validator.validate_final_layout()
→ Writer.publish()
→ 写完成日志
→ callback
```

概念伪代码如下：

```python
def run(job):
    staging = writer.begin(job.evaluation_id)
    accessions = set()
    duplicate_task.reset()

    try:
        for study in loader.iter_studies(job.dataset_path):
            context = pipeline.run_study(study)

            duplicate_task.update(study, context)
            writer.write_study(staging, context)
            validator.validate_study(staging / study.accession_number, study)

            accessions.add(study.accession_number)
            del context, study

        duplicates = duplicate_task.finalize()
        writer.write_duplicates(staging, accessions, duplicates)
        validator.validate_final_layout(staging, accessions)

        output_dir = writer.publish(staging, job.evaluation_id)
        staging = None
        callback.send_success(job.request_id, job.evaluation_id, output_dir)
        return output_dir
    except Exception:
        if staging and staging.exists():
            shutil.rmtree(staging)
        raise
```

这段代码只表达职责和顺序，不是最终补丁。

## 5. 各文件修改方案

## 5.1 `data/loader.py`

### 目标

由“返回包含全部像素数据的 `CompetitionDataset`”改为“发现数据集后逐个生成 `Study`”。

### 建议接口

新增：

```python
def iter_studies(self, dataset_path: str | Path) -> Iterator[Study]:
    ...
```

现有 `load()` 暂时保留，用于已有测试、本地工具或小数据场景，但比赛服务的 `EvaluationRunner` 不再调用它。

兼容实现可以是：

```python
def load(self, dataset_path):
    root = Path(dataset_path).expanduser().resolve()
    studies = tuple(self.iter_studies(root))
    return CompetitionDataset(root, studies, self._dataset_metadata(root))
```

注意：该兼容方法仍然是全量加载，只用于兼容，不用于正式 `/call` 链路。

### NIfTI 发现与加载

第一遍只保存轻量信息：

- 文件路径；
- accession；
- series UID；
- sidecar 路径；
- 必要的字符串元数据。

按 accession 分组后，每次只对一个 accession 调用现有 NIfTI 加载逻辑，并 `yield Study(...)`。

继续保持当前行为：

- 目录中必须存在有效 NIfTI；
- 文件名包含 `mask`、`seg`、`label` 或 `roi` 的 NIfTI 不作为输入影像；
- 图像必须为三维；
- Series UID 和 accession 继续执行安全清洗；
- 同名 JSON sidecar 解析失败时明确报错。

### Loader 的错误上下文

所有加载异常应至少包含：

- accession；
- series UID；
- 文件路径或数据集根目录；
- 原始异常类型和信息。

流式处理后，错误发生在第几个病例不再由完整 Dataset 结构体现，因此错误信息必须更具体。

## 5.2 `pipeline/inference.py`

### 目标

增加单病例推理入口，不再要求一次性接收整个 `CompetitionDataset`。

### 建议接口

新增：

```python
def run_study(self, study: Study) -> PipelineContext:
    context = PipelineContext(study=study)
    ...
    return context
```

该方法复用当前每个 Study 内部的任务循环：

```python
for binding in self.study_tasks:
    result = binding.task.predict(context)
    self._validate_result_numbers(result, binding.task.name)
    setattr(context, binding.context_field, result)
```

现有 `run(dataset)` 可暂时保留为兼容包装：

```python
contexts = {
    study.accession_number: self.run_study(study)
    for study in dataset.studies
}
```

正式比赛服务不再调用这个全量包装。

### 保持 Goal1～Goal5 独立

`StudyTask` 接口和以下结果类型保持不变：

- `Goal1Result`；
- `StitchedResult`；
- `Goal3Result`；
- `Goal4Result`；
- `Goal5Result`。

建议增加契约测试：每个 StudyTask 必须能够在仅设置 `PipelineContext(study=study)` 的情况下运行。除非比赛规则明确要求，否则一个 Goal 不应依赖另一个 Goal 已经产生结果。

### 模型权重说明

按 Study 流式加载只能降低影像和结果占用的 RAM，不能自动降低模型权重占用的 RAM 或 GPU 显存。

现有 Pipeline 在初始化时对所有任务调用 `load_model()`。如果五个真实模型同时放入 GPU，五套权重仍会常驻显存。只有测量后确认显存不足，才考虑“按 Goal 分阶段处理整个数据集并卸载模型”的第二套运行模式；首版流式改造不同时引入该复杂度。

## 5.3 `tasks/base.py` 与 Goal2 数据集级任务

### 问题

当前 `DatasetTask.predict(dataset, contexts)` 必须接收完整数据集和所有 contexts，不适合流式执行。实际受影响的是 Goal2 的重复影像检测；Goal2 的单病例拼接检测仍然是普通 `StudyTask`。

### 建议生命周期

将数据集级任务改为增量生命周期：

```python
class DatasetTask(ABC, Generic[ResultT]):
    def reset(self) -> None:
        ...

    @abstractmethod
    def update(self, study: Study, context: PipelineContext) -> None:
        ...

    @abstractmethod
    def finalize(self) -> ResultT:
        ...
```

也可以让 `reset()` 在任务构造时隐式完成，但显式 `reset()` 更适合服务重复接收多个 evaluation，避免上一次评测状态泄漏到下一次。

### DummyDuplicateTask

当前 Dummy 只需要记录排序后的前两个 accession，内存占用可以保持为常数或只保存 accession 字符串。

### 真实重复影像模型

每处理一个 Study：

```text
原始影像
→ 提取固定长度 embedding / 哈希 / 指纹
→ 保存 accession + 轻量特征
→ 释放原始影像
```

全部病例完成后：

```text
轻量特征集合
→ 相似度检索
→ 每个病例最多保留 200 个候选
→ DuplicateResult
```

如果 embedding 数量本身也可能占用大量内存，则写入 staging 下的临时特征文件或使用 `numpy.memmap`。首版不引入数据库或分布式检索服务。

## 5.4 `output/writer.py`

### 目标

将统一写出拆为可增量调用的方法，同时保留 staging 原子发布。

### 建议接口

```python
def begin(self, evaluation_id: str) -> Path:
    """创建并返回 staging 目录。"""

def write_study(self, staging: Path, context: PipelineContext) -> Path:
    """写一个病例的 prediction.json 和分割掩膜。"""

def write_duplicates(
    self,
    staging: Path,
    accessions: set[str],
    duplicates: DuplicateResult,
) -> Path:
    """写 duplicate_pairs.jsonl。"""

def publish(self, staging: Path, evaluation_id: str) -> Path:
    """将已完成且已校验的 staging 原子发布。"""
```

现有私有方法可以直接复用：

- `_write_masks()`；
- `_write_json()`；
- `_normalize_pairs()`。

`write_study()` 完成后不得保留 context、mask 或 source image 的引用。

### 改善临时目录清理

当前 `staging = write_staging(...)` 如果在 `write_staging()` 内部中途失败，赋值尚未完成，Runner 中的 `staging` 仍可能为 `None`，从而留下临时目录。

改造后先由 `begin()` 返回 staging，再逐病例写入。后续任何异常都能由 Runner 准确清理该目录。

## 5.5 `output/validator.py`

### 目标

将依赖完整数据集的统一校验拆为单病例即时校验和最终轻量校验。

### 建议接口

```python
def validate_study(self, directory: Path, study: Study) -> None:
    ...

def validate_duplicates(self, path: Path, accessions: set[str]) -> None:
    ...

def validate_final_layout(
    self,
    evaluation_dir: Path,
    accessions: set[str],
) -> None:
    ...
```

处理顺序：

1. `write_study()` 后立即调用 `validate_study()`；
2. 校验 prediction 必需字段、概率、掩膜路径、shape、affine 和二值性；
3. 校验完成后即可释放该 Study 的原始影像；
4. 全部病例结束后写并校验 `duplicate_pairs.jsonl`；
5. 最后检查 staging 中的病例目录集合与累计 accession 集合完全一致。

最终轻量校验不应再次加载全部原始影像。

## 5.6 `core/runner.py`

### 目标

Runner 成为流式生命周期的唯一编排者。

### 建议顺序

```text
写 evaluation_started 日志
→ 创建 staging
→ reset 数据集级任务
→ 遍历 loader.iter_studies()
→ 对单 Study 推理、写出、校验和释放
→ finalize 数据集级任务
→ 写并校验 duplicate_pairs.jsonl
→ 最终目录校验
→ publish
→ 写 evaluation_completed 日志
→ send_success callback
```

### 状态和异常要求

- 任一病例失败：停止后续处理；
- 删除整个 staging，不发布部分结果；
- 写 `evaluation_failed`；
- 不调用成功 callback；
- 错误日志增加当前 accession（如果已经确定）；
- 发布成功但 callback 失败时，继续保留最终输出目录，保持当前行为；
- callback 仍只在发布成功后触发。

### 内存释放

正常情况下，循环进入下一次迭代后，上一病例的局部变量应失去引用。不要默认在每个病例后调用：

```python
gc.collect()
torch.cuda.empty_cache()
```

这些调用可能显著降低吞吐量，而且不能替代正确的引用生命周期。只有通过分析确认存在无法及时回收的对象时再增加。

真实 PyTorch Task 自身应做到：

- 推理使用 `torch.inference_mode()`；
- 不把 GPU Tensor 存入长期列表或 `PipelineContext.diagnostics`；
- 返回 CPU 标量或必要的 CPU mask；
- 不保存带计算图的输出。

## 5.7 `app/server.py`

首版不需要改变 `/call` 请求和响应。

继续保持：

- 请求只做轻量校验和入队；
- `dataset_path` 必须在请求时是目录；
- 后台线程执行流式推理；
- `/call` 立即返回 `accepted`；
- 同一个 evaluation 的并发保护不变。

建议另行修复但不与流式改造绑在一起的问题：重复 `request_id` 时，`JobManager.submit()` 返回 `False`，但路由仍返回 `accepted`。该问题不是 OOM 根因，应单独提交，避免扩大本次修改范围。

## 5.8 `scripts/local_eval.py` 和 `scripts/mock_competition.py`

两个脚本继续通过 `EvaluationRunner.run()` 工作，不应直接依赖 Loader 的全量或流式实现。

`mock_competition.py` 应继续验证：

- `/health`；
- `/call` 在限制时间内响应；
- 后台生成全部结果；
- callback 在最终输出存在后到达。

## 6. 生命周期与内存边界

### 6.1 单病例生命周期

```text
磁盘
→ Study.image（RAM）
→ 模型输入 Tensor（RAM/VRAM）
→ Goal1～Goal5 Result
→ prediction.json / NIfTI mask（staging）
→ 校验
→ 删除局部引用
```

进入下一个病例前，上一病例允许长期保留的内容仅包括：

- accession 字符串；
- Goal2 重复检测的轻量特征；
- staging 中已经写入的文件；
- 少量累计计数和日志信息。

### 6.2 预期峰值

改造后的 RAM 峰值应近似：

```text
最大单病例全部序列
+ 当前序列解码临时数据
+ 当前病例 Goal5 掩膜
+ 模型 CPU 权重
+ 少量重复检测特征
```

GPU 显存峰值应近似：

```text
已加载的模型权重
+ 当前病例或当前 patch 的输入
+ 当前推理激活和临时 Tensor
```

流式 Loader 不负责解决五个模型权重同时驻留 GPU 的问题。

## 7. 输出一致性要求

流式改造前后，对同一输入和同一模型，最终目录必须保持语义一致：

```text
answer/{evaluation_id}/
├─ duplicate_pairs.jsonl
├─ {AccessionNumber}/
│  ├─ prediction.json
│  ├─ {CoreSeriesUID}/{CoreSeriesUID}.nii.gz
│  └─ {FlairSeriesUID}/{FlairSeriesUID}.nii.gz
└─ ...
```

必须保持：

- `prediction.json` 字段名称和层级不变；
- `SegmentationMaskURI` 仍相对于病例目录；
- NIfTI mask 的 shape 和 affine 与来源 Series 一致；
- `duplicate_pairs.jsonl` 至少一条合法记录；
- 单病例数据集仍按当前规则明确失败；
- 每个病例最多 200 个重复候选；
- callback 的 `predPath` 指向已发布的最终目录，而不是 staging。

## 8. 测试方案

## 8.1 单元测试

### Loader 顺序测试

使用至少三个小病例，验证：

- `iter_studies()` 每次只产生一个 `Study`；
- accession 和 Series UID 分组正确；
- NIfTI 分组、shape 和 affine 与当前结果一致；
- 非影像文件继续被跳过。

### Pipeline 单病例测试

验证 `run_study()`：

- 填充 Goal1～Goal5；
- 保持任务执行顺序；
- 拒绝非有限或越界概率；
- 不创建全局 contexts 字典。

### DatasetTask 生命周期测试

验证：

- `reset()` 清除上一 evaluation 状态；
- 每个 Study 恰好调用一次 `update()`；
- `finalize()` 只在全部 Study 完成后调用；
- Dummy 仍生成合法重复病例 pair。

### Writer 和 Validator 测试

验证：

- 单病例写出后可以立即校验；
- 一个病例失败时整个 staging 被清理；
- 最终病例目录集合必须完全匹配累计 accession；
- 只有最终校验成功才能 publish。

## 8.2 调用顺序测试

使用 Spy/Fake 组件记录事件，断言顺序类似：

```text
load A
run A
write A
validate A
load B
run B
write B
validate B
finalize duplicates
publish
callback
```

关键断言是 `load B` 不能出现在 `write A` 和 `validate A` 之前。它比在单元测试中比较不稳定的 RSS 数值更可靠地证明代码采用流式顺序。

## 8.3 端到端回归测试

继续运行现有端到端测试，并增加流式版本对照：

1. 对相同测试数据分别执行旧全量入口和新流式入口；
2. 比较 JSON、JSONL、mask shape、affine 和像素值；
3. 忽略 `ProcessingTime_ms` 等允许变化的字段；
4. 验证 callback 只出现一次且发生在 publish 之后。

兼容入口删除前，该测试可以确保流式改造没有改变比赛输出。

## 8.4 内存验收测试

构造多个尺寸相同的病例，分别测试 2、10、50 个病例。记录进程峰值 RSS。

验收标准不应要求 RSS 在每个病例后立即下降，因为 Python 和 NumPy 可能保留内存供后续复用；应检查峰值不会随病例总数近似线性增长。

预期表现：

```text
全量模式：病例数量增加，峰值 RAM 近似线性增加
流式模式：病例数量增加，峰值 RAM 接近最大单病例所需内存
```

GPU 测试单独记录 `max_memory_allocated`，避免把 RAM 和 VRAM 问题混在一起。

## 9. 分阶段实施顺序

建议拆成以下小步骤，每一步都保持可测试。

### 阶段一：建立单病例内部接口

- 增加 `InferencePipeline.run_study()`；
- 拆分 Writer 的 begin/write-study/write-duplicates/publish；
- 拆分 Validator 的单病例和最终校验；
- 现有全量入口暂时作为兼容包装。

这一阶段主要重排已有逻辑，不改变数据加载方式。

### 阶段二：改造 Goal2 数据集级任务

- 将 `DatasetTask.predict(dataset, contexts)` 改为 reset/update/finalize；
- 更新 DummyDuplicateTask；
- 增加跨 evaluation 状态清理测试。

### 阶段三：实现 Loader 流式迭代

- 增加 `iter_studies()`；
- NIfTI 按 accession 加载；

### 阶段四：Runner 切换到流式编排

- `/call` 后台链路改用 `iter_studies()`；
- 每病例推理、写出、校验后释放；
- 全部完成后处理重复任务、发布和回调；
- 保证任一失败都清理 staging。

### 阶段五：回归和内存验证

- 运行全部自动化测试；
- 对比流式与旧入口输出；
- 在接近正式数据规模的样例上记录峰值 RAM；
- 验证容器收到终止信号、callback 失败和输出目录已存在等边界情况。

### 阶段六：清理兼容代码

只有确认所有调用方都使用流式 Runner 后，才考虑删除全量兼容包装。首个可用版本不需要立即删除，以便回归比较和快速回滚。

## 10. 团队分工建议

### 基础设施负责人

负责：

- Loader 流式接口；
- Runner 编排；
- Writer/Validator 拆分；
- staging 清理和 callback 时序；
- 集成测试。

### Goal1、Goal3、Goal4、Goal5 负责人

继续只实现各自 `StudyTask` 和 Result，不需要关心数据集遍历方式。每个任务只处理传入的当前 Study。

### Goal2 负责人

分别维护：

- 单病例拼接检测 `StudyTask`；
- 重复影像检测的 reset/update/finalize 实现；
- 轻量 embedding 或指纹的内存上限。

### 集成约束

- 只有基础设施负责人修改 Runner、Loader、Writer 和 Validator；
- 只有集成人员修改 Pipeline 的最终任务注册；
- 各 Goal 不直接修改 HTTP 路由和 callback；
- 公共 Task/Result 契约变更必须先冻结，再由各模型负责人并行开发。

## 11. 风险与应对

### 风险一：单个病例仍然过大

流式处理只把上限降到单病例。如果单个 Study 包含大量高分辨率序列，仍可能 OOM。

应对顺序：

1. 确认模型实际需要哪些序列；
2. 避免加载无关序列；
3. 在单病例内做裁剪或重采样；
4. 最后才考虑 patch/切片级推理。

### 风险二：模型保存输入或中间 Tensor

即使 Loader 流式，Task 把 Tensor 放入列表、缓存或 diagnostics，也会造成内存继续增长。

应对：为每个 Task 增加多病例连续推理测试，并检查它是否长期保存输入、输出或计算图。

### 风险三：Goal2 特征无限增长

真实重复检测如果保存高维特征，内存仍可能随病例数增长。

应对：限制 embedding 维度和 dtype；超过预算时写入 staging 下的 memmap，并采用分块相似度计算。

### 风险四：流式写出后中途失败

前面病例已写入 staging，但不能作为有效最终结果发布。

应对：保持 staging 隔离；任一异常删除整个 staging；只有最终校验成功才 rename 发布。

### 风险五：吞吐量下降

逐病例读取可能增加磁盘等待，尤其是多个 Goal 分别读取或解压同一 NIfTI 时。

应对：首版优先保证内存稳定；只有性能测试证明 I/O 成为瓶颈后，再增加大小为 1 的有界预取，不直接启用无限并发。

## 12. 验收标准

代码实施完成后，应同时满足：

- `/call` 请求和响应格式不变；
- 正常请求仍快速返回 `accepted`；
- Loader 不再构造包含全部像素的 `CompetitionDataset` 供正式 Runner 使用；
- Pipeline 不再保留所有病例的 contexts；
- 每个病例在下一个病例加载前已经写出并完成单病例校验；
- 最终输出结构与当前实现一致；
- callback 只在最终输出成功发布后发送；
- 失败时不发布部分结果；
- 2、10、50 个同尺寸病例的峰值 RAM 不再随病例数近似线性增长；
- Goal1～Goal5 仍可由不同队友通过稳定的 Task/Result 接口独立开发；
- 现有测试与新增流式测试全部通过。

## 13. 明确不在本次范围内的事项

为避免一次改造过大，以下内容不与流式 Loader 同时实施：

- 多进程或多 GPU 推理；
- 分布式任务队列；
- Dask、Ray 等新的数据框架；
- 失败任务断点续跑；
- evaluation 状态持久化；
- 五个模型按 Goal 自动换入换出 GPU；
- 单病例内部的 patch 推理；
- 重复 `request_id` 返回 `accepted` 的现有行为修复。

这些事项只有在流式版本完成并通过内存测试后，依据真实瓶颈单独评估。

## 14. 推荐结论

推荐采用“Study 级顺序流式处理 + Goal2 轻量特征累计 + staging 原子发布”的方案。

该方案复用当前 `Study`、`PipelineContext`、`StudyTask`、Result、Writer 和 Validator 的既有职责，只拆分必须拆分的全量接口，不引入新的基础设施。它既能解决当前因全量影像和全量 mask 长期驻留造成的 OOM，也能保留 Goal1～Goal5 的独立开发方式。
